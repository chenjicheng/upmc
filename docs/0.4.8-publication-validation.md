# Legacy 0.4.8 publication validation

## Contract and implementation

`scripts/legacy_publication.py` only accepts source version `0.4.8`, tag
`v0.4.8`, channel `stable`, the exact tag ref, and a full lowercase commit SHA
matching both the clean source checkout and the resolved local/remote tag.
It has no user-supplied hash, size, URL, descriptor, repository, or version CLI
input. Its publication operation derives metadata from actual artifact bytes.

Release lookup uses the HTTP status returned by `gh api --include`. Only a
confirmed HTTP 404 permits creation. Authentication, transport, rate-limit,
server, malformed-response, creation and download failures stop publication.
An existing Release is immutable: the helper never uploads with `--clobber`.
It requires exactly one fully uploaded `updater.exe` with the official tagged
HTTPS URL, matching byte length, and matching API digest when available, then
downloads the asset and compares its complete SHA256 and length against the CI
artifact. The Release must be public and stable. Remote tags are resolved to
their commit, including bounded annotated-tag resolution, before and after
verification.

The initial Pages update writes identical complete descriptors to
`version.json`, `dev/version.json`, `bridge/version.json`, and
`bridge/dev/version.json`. A private Git index creates all four files and
`.upmc-legacy-transition.json` in one tree and one commit. The original CNAME
blob and unrelated tree entries remain unchanged. Missing, unexpected or
non-regular CNAME files fail; the helper never initializes Pages or copies a
fallback CNAME. It requires an existing clean Pages checkout and checks its
expected HEAD against the remote before proceeding. The final push uses an
explicit lease for that exact parent, so an intervening publisher is rejected.
Failures leave checkout files, the real index and local refs untouched. A
failed final push can leave unreachable Git objects, but publishes no commit.

The marker freezes the transition artifact. An identical rerun has no commit
or push. Different marker contents, changed bridge documents after promotion,
unexpected legacy versions, or preexisting different bridge metadata fail
instead of overwriting them.

## Test-first evidence

Base revision: `ee1b98ce8e98df6799a42a394e75438b07c09cfd`.

Command, from the repository root:

```powershell
python -m unittest discover -s scripts/tests -v
```

The first run used interface-only declarations for the new helper, each
raising an explicit unimplemented-behavior error. This permitted tests to
execute against the missing publication behavior without treating import or
dependency failures as RED. The baseline workflow was unchanged at this point.
Result: 18 tests ran; 8 valid-path tests failed because descriptors, source
validation, explicit Release lookup, verified Release handling and atomic
four-document publication were not implemented. Negative cases that already
failed closed were not claimed as separate RED evidence.

After implementation, the same command passed all 18 tests. The suite uses
temporary byte fixtures and actual local Git repositories, a bare remote,
rejected-push hooks and a real concurrent ref update. Only external `gh`
effects are simulated. No tests upload assets, create public Releases, update
remote repository branches or contact a running updater.

Coverage includes actual-byte metadata, exact version/tag/build/ref/channel
checks, missing/empty artifacts, invalid URLs, invalid descriptor integrity
fields, false/missing Release assets, mismatched/truncated downloads, explicit
404 versus API/auth/transport failures, CNAME byte preservation, one-commit
four-document publication, failed pushes, stale/concurrent Pages updates,
idempotent reruns and refusal to rewind later bridge promotion.

Read-only verification of the installed GitHub CLI against the actual public
`v0.4.7` Release confirmed the `HTTP/2.0 200 OK` header format used by the
parser. No network mutation was performed during author validation.

## Native promotion boundary

This is a legacy HTTPS-origin transition. SHA256 and size authenticate neither
the publisher nor a TUF root. This workflow requires no production TUF secret,
does not alter `upmc-server`, and does not change Packwiz or proxy DLL protocols.

Later native promotion must update only `bridge/version.json` and
`bridge/dev/version.json`; preserve both original entry documents and the
transition marker at 0.4.8. A workflow file on another branch is independent of
this file. Before pushing native/dev publication changes, review that branch's
publisher and its path/channel guards: this maintenance workflow cannot stop a
different workflow from overwriting the frozen files. Use the same Pages
concurrency group and a fresh expected parent with an explicit push lease.

## Release prerequisites and remaining acceptance

- The independently reviewed client version bump and bridge/helper changes
  must be integrated before tagging. This author's isolated branch still has
  client version 0.4.7; temporary fixtures use 0.4.8 and genuine fixture commit
  SHAs. No production SHA or secret is fabricated.
- The release operator must run integration/client tests and create the actual
  `v0.4.8` tag only at the accepted integrated commit. A tag or public Release
  must not be moved or have its executable overwritten to repair a failed run.
- Existing `tools` assets remain runtime inputs for legacy configuration where
  referenced. They are not build-time inputs: both matching proxy DLLs are built
  from this source tree and embedded by `include_bytes!`. This publisher never
  changes the `tools` Release.
- `UPMC_SUB_URL` remains an optional build input. Existing optional Authenticode
  credentials are not a TUF key; absent credentials produce an unsigned Windows
  executable. Record whether signing ran, and derive integrity after signing.
- Local helper tests do not establish a successful Windows release build,
  public CI run, public asset download, Pages propagation, real installation or
  native migration. Those gates remain with the primary release operator.
