`selfupdate_bridge_tests.rs`. The original inline build-ID decision was extracted
unchanged into a callable test seam; its version/channel arguments were initially
unused. This was a compiling seam, not an implemented SemVer policy.

`cargo test -p upmc bridge_tests -- --nocapture` against the original decision and
reader: **3 passed, 5 failed** (exit 101). Exact failures included:


After implementing required schema validation, the official Release/proxy URL
allowlist and SemVer precedence (including build-metadata equality), the same
command passed **8/8**. The old reader compatibility test still recognizes the
new commit and ignores added fields. A local dev build with no explicit build ID
does not replace itself solely for an equal-version remote build.

Raw command output is retained locally in `.validation/01-discovery-red.txt`,
`.validation/02-discovery-green.txt` and `.validation/03-discovery-regression.txt`.
These generated logs are not release inputs.

The bridge remains HTTPS-origin trusted; SHA256 and size are integrity checks,
not signatures. No native protocol, downloaded trust root, CAS, TUF or server

The audited `14eadd0` helper and health-ack implementation was adapted from the

tests were removed. Existing audited tests were retained as regression coverage,
not relabeled as tests newly proven RED on the legacy interfaces. The new legacy
fixtures only gained an expected-identity argument when adapting to the repaired
helper; their preservation assertions stayed unchanged.

`cargo test -p upmc selfupdate -- --nocapture` passed **64 tests**, with one
subprocess-fixture test ignored in the top-level harness and explicitly invoked
by the mapped-helper test. Coverage includes real Windows mapped-process
ownership, competing OS file locks, atomic replacement, staging/installed digest
failure, candidate launch failure/early exit/timeout, stop-before-rollback,

## Bounded transfer and caller error propagation

The old transfer loop and retry policy were extracted into callable seams before
replacement, preserving their unbounded reads, create/truncate behavior and
retry-every-error policy. `cargo test -p upmc transfer_tests -- --nocapture`
produced **3 passed, 4 failed** (`09-transfer-red.txt`): a 15-byte manifest caused
1,000,000 response bytes to be read, existing staging was overwritten, truncated
bytes remained staged, and HTTP 400 was retried three times. After the change,
the original seven tests passed (`11-transfer-green.txt`).

Staging now uses exclusive creation, reads at most the advertised length plus
one excess-byte probe, syncs the file, and verifies PE magic, exact length and
SHA256 before helper creation. Rejected staging is removed only when this
operation created it. Secondary cleanup errors are recorded with both failures.
Only typed transport timeouts, explicit transient socket errors and HTTP
408/429/500/502/503/504 can retry; permanent metadata, integrity, TLS, URL,
filesystem and other HTTP errors stop immediately. There is no final sleep.
Requests keep the 30-second metadata / 600-second artifact timeout and three
attempt limits; HTTPS is required throughout redirects. Metadata reads are
limited to 16 KiB. There is no legacy-endpoint or native-protocol fallback.

The old coordinator match was similarly extracted without changing behavior.
`cargo test -p upmc self_update_gate_tests -- --nocapture` produced **1 passed,
1 failed** (`10-propagation-red.txt`): rejected metadata invoked downstream game
work once. GREEN (`12-propagation-green.txt`) returns the original typed error,
emits `selfupdate.rejected` with full context, and invokes no game/Packwiz work.
No-update invokes game work once; helper handoff invokes none.

Additional real loopback HTTP fixtures validate a 503 followed by a complete
manifest on the same endpoint, a typed 40 ms timeout, truncated HTTP bodies and
production rejection of HTTP. These fixtures inject a test-only local HTTP
agent; production endpoints remain fixed HTTPS. The first full-suite run exposed
Windows accepted sockets inheriting nonblocking mode (`15-final-client-tests.txt`);
the fixture now explicitly restores blocking reads. This was a fixture issue,
not a claimed production behavioral RED.

## First hop, future handoff and final local gates

The first hop uses the already deployed 0.4.7 helper. It does **not** acquire the
new transaction lock or pass health flags. A dedicated Windows fixture maps the
legacy helper filename without a new lock, then invokes normal-startup cleanup:
cleanup emits its diagnostic, remains nonfatal, and preserves active helper and
staging files. After the old helper exits, cleanup succeeds. The initial
equal-version/equal-build 0.4.8 manifest performs no replacement. Persisted dev
settings, including legacy extra fields, survive an unflagged first-hop launch
and select `/bridge/dev/version.json` without rewriting the settings file.

For the later handoff, real isolated child processes exercise successful V1
acknowledgement, early exit, withheld acknowledgement, and confirmed termination.
The two ignored test entrypoints are subprocess fixtures explicitly launched by
non-ignored parent tests; neither invokes the application GUI or installed data.
This checks the shared wire contract, not an end-to-end native installation.
