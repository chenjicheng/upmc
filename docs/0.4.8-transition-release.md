# UPMC 0.4.8 transition release

## Scope and release line

Build on the published legacy 0.4.7 source (tag `v0.4.7` at `d0e2f59`; the identical source tree on `main` is `57d4758`). Keep Packwiz, existing installation paths, game-server discovery, user channel selection, and the existing matching proxy DLL pair. The independently audited native 0.6.0 work remains on `dev`. This release does not require changes to `upmc-server` or activate native game distribution.

The release prepares the updater handoff. It does not manufacture a native installation state, rewrite a legacy pack into a native release, or claim that a real legacy game installation has completed the later native migration.

## Two-step distribution

Existing legacy clients continue to discover `0.4.8` through the original `/version.json` (and `/dev/version.json`) on `upmc.chenjicheng.cn`. Preserve their accepted `download_url`, `build_id`, and `sha256` fields. Their build-ID comparison must recognize the new artifact without changing old binaries.

Starting with 0.4.8, self-update discovery uses `/bridge/version.json` for stable and `/bridge/dev/version.json` for dev. Publish both bridge documents with the same 0.4.8 artifact initially. No missing-endpoint fallback or automatic native-server switch is needed. Later native promotion changes only the bridge documents, keeping the legacy entry documents at 0.4.8 so existing clients first receive the repaired updater.

The transition document carries `version` (SemVer), `build_id` (commit SHA), `download_url` (official HTTPS Release artifact or its existing approved proxy), `sha256` (64 hex digits), and `size` (positive byte length). Malformed or missing integrity fields must fail before staging or replacing an executable. Version ordering prevents downgrades; stable requires a newer SemVer for replacement, while dev may additionally accept a different explicit build ID at the same version. A same-build normal response performs no replacement.

This bridge inherits the legacy HTTPS-origin trust boundary. SHA256 and size verify artifact integrity; they are not signatures. Native 0.6.0 must subsequently enforce its own embedded production TUF root and signed publication contract. This release must not silently trust a downloaded TUF root or claim that the bridge is TUF-authenticated.

## Replacement and failure semantics

Use the audited native updater's compatible helper/health-ack contract where practical. Validate target/source/helper ownership, artifact size and digest before replacement, preserve a recoverable old executable, and require positive startup acknowledgement. Rollback may occur only after the candidate is proven stopped; preserve original and recovery errors when either phase fails. Retries must be finite and restricted to genuinely transient failures. Preserve the validated same-target omitted `--restart` compatibility contract.

Any changed runtime fallback must emit structured diagnostics with a stable identifier, reason, primary/fallback paths, original error, context and counter. Approved correctness-preserving recovery may WARN; other unexpected/degraded outcomes use ERROR. A failed update cannot be reported as an ordinary successful update or silently fall through into a different distribution protocol.

Startup health acknowledgement must not cause the helper or a new process to delete active transaction files or another process's helper. Tests must cover the old discovery reader, normal/no-update cases, exact version/build conditions, malformed metadata, hash/size mismatch, truncated download, bounded timeout/retry, concurrent helpers, candidate failure, rollback failure, and the health contract shared with native 0.6.0. Use isolated test fixtures rather than launching the live updater against the user's game directory.

## Publication and acceptance

Validate the client and publication workflow before tagging. The stable release artifact and all four Pages entry documents must refer to the same built bytes and commit; derive length/hash from the artifact, not unchecked input. Resolve Release/API errors explicitly, preserve the existing Pages CNAME and unrelated files, and avoid publishing incomplete manifests. Keep older entry documents frozen during future native promotion.

Each implementing sub-agent uses a separate worktree/branch, writes behavioral tests before implementation, and produces cohesive commits. An independent Review Agent reviews exact commits; only the primary agent integrates approved commits. After integration, rerun the relevant gates, publish `v0.4.8`, and verify CI, the public Release artifact, Pages metadata, and public download integrity. Report any unavailable real-installation/native-server validation separately.
