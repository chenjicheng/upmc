# 0.5.6 named-mutex transaction lock

## Scope

The self-update transaction lock is a Windows named mutex instead of a
persistent `exe.update.lock` file. New normal startup, update, and helper paths
leave no lock file behind. A transient compatibility file may exist only for the
duration of an active transaction so an old 0.4.8-0.5.5 opener is still
excluded.

## Naming and ownership

- Name: `Global\UPMC.SelfUpdate.<sha256(normalized target path)>`, with ASCII
  case folding of the hash input. An existing target is canonicalized in full so
  case-only, 8.3 short-name, `..`, and parent-junction aliases of one directory
  entry share one identity. If the target is temporarily absent during
  replacement or recovery, the canonical parent plus the given basename is used,
  so identity never requires the file to exist and never keys on a file ID. The
  same normalized path names the legacy `exe.update.lock`, so both keys agree.
- The identity is always the normalized path, never a file ID. Aliases of one
  directory entry (case, 8.3 short name, `..`, parent junctions) unify, and a
  reparse point follows to its final target; distinct hard-link directory
  entries stay independent because replacement rewrites one directory entry.
  Target and legacy-lock reparse safeguards are unchanged.
- `CreateMutexW` uses a `NULL` security descriptor: the default DACL derived
  from the current process token, with a non-inheritable handle. No `Everyone`
  ACE is installed. Any creation or open failure, including an inaccessible
  existing object, fails the transaction closed. Validation and existing
  subprocess tests ran under a medium, non-elevated token; cross-account sharing
  is not claimed and would fail closed.
- The RAII guard is `!Send + !Sync` (Win32 mutex ownership is thread-affine) and
  releases the mutex exactly once per successful acquisition. The legacy handle
  is closed before the mutex is released so the next acquirer never observes a
  stale exclusive guard.

## Legacy compatibility

- Existing `exe.update.lock`: `OPEN_EXISTING` with `share_mode(0)` and
  `FILE_FLAG_OPEN_REPARSE_POINT`. A merely preopened old handle blocks the open
  even before its byte-range lock is taken. Validation is bound to the exclusive
  handle: regular file, no reparse point, not a directory, zero length. Only a
  validated file is marked delete-pending with classic `FileDispositionInfo`;
  the name is never removed by pathname, never truncated, and POSIX unlink is
  never used.
- Absent `exe.update.lock`: `CREATE_NEW` with `FILE_FLAG_DELETE_ON_CLOSE`. This
  closes the old-vs-new absent-file race and guarantees no leftover on normal
  release, unwind, or abrupt process death. `AlreadyExists` is distinguished
  from fatal create errors and retried against the existing file.
- Retries are bounded and sleep only between transient sharing/lock-contention
  and delete-pending errors. Nonempty, reparse, directory, and other permanent
  failures stop immediately and retain the item.

## Health migration

For an incoming 0.5.x parent using the `self_update` library, the candidate
acknowledges health first and then performs a bounded, deferred, legacy-lock-only
cleanup:

- The acknowledgment callback runs before any filesystem work; a failed
  acknowledgment returns immediately with no mutation, and a committed
  acknowledgment is never suppressed by a cleanup error.
- `library::ensure_process_can_update()` is rechecked before cleanup and again
  after protection is acquired.
- A still-held old lock is retained within the bounded budget; a released or
  crashed holder is migrated away.
- Helper, rollback backup, and staging artifacts are owned by
  `legacy_cleanup::ParentProof` and are never touched here; the exact-helper
  proof cleanup is unchanged.

## Known limits

- Full canonicalization resolves aliases only while the target exists. For a
  temporarily absent target, the fallback folds ASCII case only; a Unicode
  case-differing name for a missing directory entry is not a single on-disk
  identity.
- A machine-wide target shared across different user accounts fails closed when
  the default DACL does not grant access to the second account.
- This note is a technical design record, not a release or acceptance claim.
